## 1412 调查

诊断归类为 **CHARACTERIZED**。应用采用窗口优先关闭后，最终六次采样均未出现诊断。相同版本的最小 Wails 程序仍能通过直接调用 `App.Quit()` 复现。

所有对照使用 Windows 11 25H2 build 26200、Wails v3.1.0 和 WebView2 157.0.4341.42。最小程序只创建 WebView 和静态页面，两个退出变体使用同一个二进制。它没有 DeskPilot 服务绑定、Vue 事件订阅、任务线程或 SQLite。

| 样本 | 退出码 | 1412 出现次数 | 释放检查 |
|---|---|---|---|
| 归档 Phase 1 可执行文件 | 0 / 0 / 0 | 3 / 3 | 归属 WebView2 残留 0 |
| 最小程序直接 `App.Quit()` | 0 / 0 / 0 | 3 / 3 | 归属 WebView2 残留 0 |
| 最小程序 `Window.Close()` | 0 / 0 / 0 | 0 / 3 | 归属 WebView2 残留 0 |
| 最终应用正常验收退出 | 0 / 0 / 0 | 0 / 3 | 关闭顺序通过，可独占打开 SQLite，归属 WebView2 残留 0 |
| 最终应用有待审批任务时关闭窗口 | 0 / 0 / 0 | 0 / 3 | 关闭顺序通过，审批失效，执行记录数为 0，目标文件不存在 |

Windows 1412 对应 `ERROR_CLASS_HAS_WINDOWS`。固定版本的 Wails 源码显示，`App.Quit()` 的清理会触发窗口关闭事件并结束消息循环。Windows 正常窗口关闭路径调用 WebView2 适配层的 `ShuttingDown()`，随后销毁原生窗口。适配层另有显式关闭控制器和释放 COM 引用的内部路径，应用通过公开 API 取得的是窗口句柄。对照结果支持这样的归因：直接退出的消息与窗口清理顺序会使 Chromium 尝试注销仍有关联窗口的类。这个定位来自可复现的路径差异和源码顺序，未测量 WebView2 Environment 或 Controller 的 COM 引用计数。

采样记录 PID、UTC 启停时间、退出码、原始 stderr 和有序生命周期事件。WebView2 进程通过独立配置目录、创建时间和父 PID 归属到样本。部分子进程在宿主退出的首个采样时仍可见，随后自行退出。通过样本在有界的释放检查内未观察到归属进程残留，SQLite 关闭和注册表句柄释放发生在退出前。现有证据支持继续使用固定版本和公开的窗口关闭路径。跨 Windows 版本或 WebView2 版本的退出表现仍待验证。

## 生命周期与取消

1. 窗口关闭或应用退出请求先关闭业务调用入口，发出生命周期取消信号并断开事件投递。
2. 后台关闭路径等待已接收调用、任务工作线程和审批到期线程。SQLite 在此期间保持可用。
3. 保存剩余任务状态，关闭 SQLite 和配置目录锁，再释放注册表的目录句柄。存储失败保留错误码并反馈给日志和进程退出码。
4. 通过 Wails 关闭窗口。窗口从管理器移除后再调用 `App.Quit()`，运行 Wails 的关闭钩子。窗口移除延迟会记录并继续等待公开关闭路径。
5. 前端在重连、页面离开或组件卸载时取消其事件订阅，释放媒体查询监听。重复退出请求复用同一个关闭流程。

任务取消不等待 Mock 回复。执行器在文件写入和原子重命名边界检查取消。未提交的临时文件按持有的句柄清理，提交后的文件保留。重复取消不会追加同一审计记录。待核查任务不会被 StopAll 改成确定结论。同步系统 I/O 若长时间阻塞，仍可能延迟有序退出。

## SQLite 事务与故障

| 业务边界 | 同一事务中的记录 |
|---|---|
| 创建任务 | 任务、初始步骤、用户消息与审计。进入规划后持久化规划状态 |
| 保存计划与待审批 | 任务与步骤、原始操作与审批、回复消息和审计 |
| 接受审批 | 已批准状态、运行中任务、工具执行记录和审计 |
| 消费审批 | 精确操作的单次 CAS、关联原执行记录的 `file_intents` 行和消费审计 |
| 原子重命名前 | 独立短事务保存已刷新临时文件的原生身份 |
| 最终结果 | 任务与步骤、工具执行证据、回复、审计及意图结算 |
| 重启核查 | 原任务和执行记录的核查结论、审批失效或原消费状态、审计及可结算意图 |

文件 I/O 在 SQLite 事务外进行。失败的 SQLite `COMMIT` 曾在同一池连接上暴露未提交记录。现在事务保留专用连接，提交失败后在原连接回滚，回滚失败则丢弃该连接。连接级外键、忙等待和 `synchronous=FULL` 在连接重建时重新应用。配置目录锁阻止并发的 SQLite 恢复实例。

Schema v1 的 SQL 保留，v2 通过单独事务增加 `file_intents` 表、关联约束和待结算索引。失败或中断会回滚该版本的 DDL 和版本号。历史数据库副本在实际桌面应用中迁移后通过 10 项旧历史恢复断言，源数据库哈希保持一致。 [迁移记录](phase2a-evidence/migration-v1-summary.json)

| 故障 | 处理 |
|---|---|
| `STORAGE_BUSY` | 短时争用，可在阻塞事务结束后重试业务请求 |
| `STORAGE_READ_ONLY`、`STORAGE_FULL`、`STORAGE_IO`、`STORAGE_UNAVAILABLE` | 返回存储错误。修复权限、空间或连接后，可重启核查未结算意图 |
| `STORAGE_CONSTRAINT` | 回滚当前事务，记录真实失败。消费事务失败时不会发生文件提交 |
| `STORAGE_CORRUPT`、`STORAGE_SCHEMA_VERSION` | 停止打开或迁移，保留数据库供兼容版本或人工处理 |

已测试 Windows 只读文件属性、SQLite 写锁、页数限制产生的真实 `SQLITE_FULL`、关闭连接、延迟外键提交失败、迁移失败与中断、截断或无效数据库。页数限制用来注入存储满错误，未填满系统磁盘。文件已经提交而最终数据库事务失败时，当前会话显示 `RECOVERY_REQUIRED`、已知文件结果及存储错误。原持久化执行和意图保留，供重启核查。

## 文件提交恢复

唯一可执行工具仍为 `filesystem.file.create`。临时文件写入和刷新后，记录卷序列、128 位文件 ID、创建时间及内部临时名称。这个见证在重命名前提交到 SQLite。原生身份不可用或见证无法保存时，执行器结束当前操作并清理持有的未提交文件。

恢复引擎在业务入口开放前检查未完成任务及未结算意图。它使用原审批路径和已绑定的操作数据，在固定工作目录内只读打开目标，核对原生身份、规范路径、字节数、内容和 SHA-256。原工具执行 ID 和审批 ID 保留。原审批已消费时，恢复始终保留消费状态。模型不会参与核查，也不会重新调用执行器。

| 重启时的证据 | 恢复状态 |
|---|---|
| 未消费审批，或 v2 意图尚未写入见证 | `PAUSED`，已记录取消的任务保持取消。没有通过提交前门槛 |
| 原始身份、路径、内容均匹配 | 补记独立验证和结算。已记录取消时保留 `CANCELLED` 及文件证据 |
| v1 已消费操作无见证，或目标缺失、身份不同、内容不符 | `RECOVERY_REQUIRED`，保留原记录与当前核查结果 |
| 最终结果已持久化 | 保留完成或取消的历史 |

同名同内容文件不能通过身份核查。已核查的结果只证明检查时原文件位于批准路径，无法还原外部移动行为或准确提交时间。见证前的进程中断可能留下临时文件，自动核查保留这些未确认归属的文件。匹配证据不足的操作保持人工处理状态。
